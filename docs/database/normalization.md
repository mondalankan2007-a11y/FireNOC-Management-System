# Database Normalization to Third Normal Form

Normalization analysis of the FireNOC Management System schema. The tables
examined here are defined in [relational-schema.md](relational-schema.md); the
entities and relationships are in [er-model.md](er-model.md).

The analysis proceeds relation by relation through first, second and third
normal form, states where the schema already conforms, and sets out the
decomposition that brings the remaining relations to 3NF.

---

## 1. Method and notation

`A → B` is read "A functionally determines B": any two rows agreeing on `A`
must agree on `B`.

A relation is in

- **1NF** if every attribute holds a single atomic value and there are no
  repeating groups.
- **2NF** if it is in 1NF and no non-prime attribute is functionally dependent
  on only part of a candidate key.
- **3NF** if it is in 2NF and no non-prime attribute is transitively dependent
  on a candidate key — equivalently, for every non-trivial `X → Y`, either `X`
  is a superkey or every attribute in `Y` is prime.

The eleven application-owned relations are analysed. Django's own framework
tables (`auth_group`, `auth_permission`, `django_content_type`,
`django_session`, `django_admin_log`) are generated by the framework and are
outside the project's design.

Every table in this schema uses a database-generated surrogate primary key
(`id`). A surrogate key determines every other attribute in its row by
construction, so the interesting dependencies are the ones that hold **between
non-key attributes**. Those are what the analysis below looks for.

---

## 2. First normal form

All eleven relations satisfy 1NF.

| Check | Result |
|---|---|
| Multi-valued attributes (lists in one column) | None |
| Repeating groups (`item1`, `item2`, `item3` columns) | None |
| Composite attributes stored as one column | None |
| Every relation has a primary key | Yes |

Two design decisions deserve note, because they are the places where a schema
usually fails 1NF and this one does not:

- **Checklist items are rows, not columns.** An inspection assesses twelve
  fire-safety items. A common wrong design adds twelve boolean columns to
  `officers_inspection`. Here each item is a row in
  `officers_inspectionchecklistitem` with a `(inspection_id, item_type)`
  uniqueness rule, so adding a thirteenth item needs no schema change.
- **Documents are rows, not columns.** Supporting files live in
  `applicants_applicationdocument` rather than as `document1_file`,
  `document2_file` columns on the application.

`applicants_application.building_address` stores a street address as free text
while `city`, `state` and `pin_code` are separate columns. An address line is
treated as atomic here, which is the normal convention; splitting it into house
number, street and locality would serve no query in this system.

---

## 3. Second normal form

All eleven relations satisfy 2NF, and for most of them trivially so.

A 2NF violation requires a **composite** candidate key, so that a non-prime
attribute can depend on part of it. Ten of the eleven relations have only
single-attribute candidate keys (`id`, and in two cases a business key such as
`application_id` or `officer_id`). A partial dependency is impossible in those
relations.

One relation has a composite candidate key:

**`officers_inspectionchecklistitem`** — candidate keys `{id}` and
`{inspection_id, item_type}`.

| Dependency | Depends on the whole key? |
|---|---|
| `{inspection_id, item_type} → status` | Yes. The compliance result is the result *of that item on that visit* |
| `{inspection_id, item_type} → remarks` | Yes, for the same reason |
| `{inspection_id, item_type} → created_at, updated_at` | Yes |

No attribute depends on `inspection_id` alone or on `item_type` alone, so the
relation is in 2NF.

---

## 4. Third normal form

Nine of the eleven relations satisfy 3NF. Two do not: `applicants_application`,
which is decomposed below, and `officers_deficiency`, whose redundancy is
retained deliberately.

### 4.1 Relations already in 3NF

`auth_user`, `officers_officerprofile`, `applicants_applicationdocument`,
`officers_documentverification`, `officers_applicationreview`,
`officers_inspection`, `officers_inspectionchecklistitem`,
`officers_inspectionreport` and `officers_deficiencyrectification` have no
non-trivial functional dependency whose determinant is not a superkey. Each
non-key attribute describes the entity the row represents and nothing else.

`officers_inspection.location` deserves a specific note, because it looks like a
copy of `applicants_application.building_address` and is populated from it by
default. It is not a transitive dependency: the column exists precisely so an
inspection can record a site address that *differs* from the address on the
application, which the field's own definition states. Two rows with the same
`application_id` may legitimately hold different locations, so
`application_id → location` does not hold.

### 4.2 Violation V1 — postal code determines city and state

Relation: `applicants_application`

```
id → pin_code
pin_code → city, state
```

`pin_code` is not a superkey of `applicants_application`, so `city` and `state`
are transitively dependent on the primary key. This is the textbook form of a
3NF violation.

**Consequences.** The city and state for a postal code are stored once per
application rather than once per postal code. Two applications quoting the same
pin code can disagree about the city, and nothing in the database prevents it.
Correcting a mis-spelled city name requires an update across every application
row that mentions it.

### 4.3 Violation V2 — applicant identity repeated on every application

Relation: `applicants_application`

```
id → applicant_id
applicant_id → full_name, email
```

`full_name` and `email` are copied onto the application at submission time from
the signed-in user's `auth_user` row. They are therefore determined by
`applicant_id`, which is not a superkey of `applicants_application`.

`mobile_number` is a different case and must be separated from the other two.
It is typed into the application form on every submission and is **not stored
anywhere else in the schema** — `auth_user` has no telephone column and
applicants have no profile table. So the mobile number is not redundant with an
existing relation; it is an applicant attribute with no home, re-entered from
scratch each time.

**Consequences.** An applicant who corrects their name or email on their account
leaves every previously submitted application showing the old value. An
applicant who files five applications stores five copies of their telephone
number, with no way to answer "what is this applicant's current contact
number?" other than by picking the most recent application.

A counter-argument deserves recording, because it is a reasonable reading. These
columns can be understood as a deliberate *point-in-time snapshot*: the contact
details as given at submission, frozen for the audit record, in the same way an
invoice freezes a delivery address. Under that reading `applicant_id → full_name`
does not hold, because the stored value is intentionally historical and may
differ from the current one.

The snapshot reading is rejected here for one reason: nothing in the schema or
the code treats these columns as historical. They are not immutable, there is no
separate "current details" source to contrast them with, and the application form
pre-fills them from the live user record on every submission, which is the
behaviour of a cache rather than of an archive. A genuine snapshot design would
keep both: a normalized applicant record *and* a frozen copy on the application.

### 4.4 Violation V3 — building attributes have no entity

Relation: `applicants_application`

```
{building_address, pin_code} → building_name, building_type, building_type_other,
                               num_floors, builtup_area, year_construction,
                               occupancy_type
```

A physical building at a given address has one name, one construction year, one
built-up area and one floor count. Those nine columns describe the *building*,
not the *application*, and `{building_address, pin_code}` is not a superkey of
`applicants_application`.

**Consequences.** `RENEWAL` is one of only two application types this system
supports, so re-applying for the same building is a designed-for, routine event
— and every renewal duplicates all nine columns. A building that is extended
by a floor must be corrected in every application row that refers to it, and
nothing prevents two applications for the same address from disagreeing about
how many floors it has.

This is the most consequential of the three violations, because it is the one
the system's own workflow guarantees will happen.

### 4.5 Retained redundancy — `officers_deficiency.application_id`

Relation: `officers_deficiency`

```
id → inspection_id
inspection_id → application_id
```

Every deficiency is created with `application = inspection.application`, so the
application reference is derivable by following the inspection. Formally this is
a transitive dependency and therefore a 3NF violation.

It is **retained deliberately**, and not corrected by the decomposition below.
Deficiency lists are filtered by application on every officer and applicant
screen in the system, and the direct foreign key removes a join from the most
frequent query in that module. Because the value is always assigned from the
inspection in a single code path, the two can only diverge if a row is written
by something other than the application.

This is a reasoned trade of normal form against query cost, which is a normal
thing for a physical schema to do. What makes it defensible rather than sloppy
is that the invariant is written down and will be enforced: the constraints work
later in this module adds a database-level check that a deficiency's application
matches its inspection's application, so the redundancy cannot become an
inconsistency.

## 5. Target decomposition

Three new relations resolve V1, V2 and V3.

### 5.1 `PinCode` — resolves V1

| Column | Type | Constraints |
|---|---|---|
| `pin_code` | varchar(10) | PRIMARY KEY |
| `city` | varchar(100) | NOT NULL |
| `state` | varchar(100) | NOT NULL |

The postal code is a genuine natural key, so no surrogate is introduced. `city`
and `state` are stored once per postal code.

### 5.2 `ApplicantProfile` — resolves V2

| Column | Type | Constraints |
|---|---|---|
| `id` | bigserial | PRIMARY KEY |
| `user_id` | integer | REFERENCES `auth_user`, UNIQUE, NOT NULL |
| `full_name` | varchar(150) | NOT NULL |
| `mobile_number` | varchar(15) | NOT NULL |
| `created_at` | timestamptz | NOT NULL |
| `updated_at` | timestamptz | NOT NULL |

One row per applicant. `email` is not duplicated here: `auth_user.email` is
already the single authoritative copy, and adding a second one would recreate
the problem this relation exists to remove. `mobile_number` moves here because
this is the first place in the schema where it has a home.

### 5.3 `Building` — resolves V3

| Column | Type | Constraints |
|---|---|---|
| `id` | bigserial | PRIMARY KEY |
| `name` | varchar(150) | NOT NULL |
| `address` | text | NOT NULL |
| `pin_code` | varchar(10) | REFERENCES `PinCode`, NOT NULL |
| `building_type` | varchar(50) | NOT NULL |
| `building_type_other` | varchar(100) | |
| `num_floors` | integer | NOT NULL, CHECK > 0 |
| `builtup_area` | numeric(10,2) | NOT NULL, CHECK > 0 |
| `year_construction` | integer | NOT NULL |
| `occupancy_type` | varchar(50) | NOT NULL |
| `created_at` | timestamptz | NOT NULL |
| `updated_at` | timestamptz | NOT NULL |

- `UNIQUE (address, pin_code)` — one row per physical building.

With `pin_code` a foreign key to `PinCode`, the city and state are reached
through the building and are stored exactly once.

### 5.4 Resulting `Application`

`applicants_application` keeps only what genuinely describes the application:

```
Application(id, application_id, applicant_profile_id, building_id,
            application_type, purpose, remarks, status,
            created_at, updated_at)
```

Fourteen of the twenty-three columns move out — three applicant, nine building
and two location — and `applicant_id` is replaced by `applicant_profile_id`.
Every remaining non-key attribute describes the application itself, so the
relation is in 3NF.

---

## 6. Boyce-Codd normal form

The decomposed relations are also in BCNF.

BCNF requires every non-trivial determinant to be a superkey. In each new
relation the only non-trivial determinants are the declared keys:
`pin_code` in `PinCode`; `id` and `user_id` in `ApplicantProfile`; `id` and
`(address, pin_code)` in `Building`. Each is a candidate key, so no relation
separates BCNF from 3NF here.

The decomposition is **lossless** — every split is along a functional dependency
whose determinant becomes the primary key of the new relation, so joining the
parts on the foreign key reproduces the original rows exactly — and it is
**dependency preserving**, since each of V1, V2 and V3 becomes a key constraint
in the relation that now owns it.

---

## 7. How the change is applied

The schema is live, with the applicant and officer modules reading these columns
across more than two thousand lines of view code and the existing test suite
asserting on them. The decomposition is therefore applied **additively**:

1. Create `PinCode`, `ApplicantProfile` and `Building`, and add nullable
   `building_id` and `applicant_profile_id` foreign keys to `Application`.
2. Backfill the new tables from the existing application rows with a data
   migration, de-duplicating buildings by `(address, pin_code)`.
3. Leave the original columns on `Application` in place and populated.

The backfill reconciles rather than copies, because the existing rows were
written by a form that never required them to agree with one another. Three
rules apply, each stated in the migration itself:

- **Most recent wins.** Where applications disagree about the same postal code,
  building or applicant, the newest application's values are kept.
- **Keys match loosely, values store verbatim.** Addresses and postal codes are
  compared with whitespace collapsed and case ignored, so `12 MI Road` and
  `12  mi road` resolve to one building; the row keeps the newest spelling.
- **Unusable rows are skipped, not repaired.** `Application` permits
  `num_floors` and `builtup_area` of zero and `Building` forbids both, so such
  an application keeps its denormalized columns and its `building_id` stays
  null. Inventing a plausible floor count would corrupt the record silently.

The migration is reversible: unapplying it unlinks the applications and empties
the three tables, which is safe because the preceding migration created them
empty and the denormalized columns are never modified.

**Known gap.** The backfill populates the normalized tables from data that
exists when it runs. Nothing yet keeps them in step with applications submitted
afterwards, because the applicant module writes only the denormalized columns.
Until the admin screens write through these tables, a new application will have
`building_id` and `applicant_profile_id` null.

The original columns are not dropped. Dropping them would break working code in
two modules this module does not own, for no benefit the project can collect
before submission. The normalized tables become the authoritative source for new
work — admin reporting, the monitoring queue and NOC issuance — while existing
code continues to read the columns it was written against.

What this means in normal-form terms should be stated plainly rather than
glossed: until the original columns are removed, `applicants_application` itself
remains unnormalized, and the schema holds the data twice. The design is in 3NF;
the deployed table will reach it when the dependent code is migrated. Recording
that honestly is more useful than claiming a conformance the schema does not yet
have.

## 8. Summary

| Relation | 1NF | 2NF | 3NF | Action |
|---|:---:|:---:|:---:|---|
| `auth_user` | Yes | Yes | Yes | None |
| `officers_officerprofile` | Yes | Yes | Yes | None |
| `applicants_application` | Yes | Yes | **No** | Decompose: V1, V2, V3 |
| `applicants_applicationdocument` | Yes | Yes | Yes | None |
| `officers_documentverification` | Yes | Yes | Yes | None |
| `officers_applicationreview` | Yes | Yes | Yes | None |
| `officers_inspection` | Yes | Yes | Yes | None |
| `officers_inspectionchecklistitem` | Yes | Yes | Yes | None |
| `officers_inspectionreport` | Yes | Yes | Yes | None |
| `officers_deficiency` | Yes | Yes | **No** | Retained by choice; constraint added |
| `officers_deficiencyrectification` | Yes | Yes | Yes | None |

Three new relations — `PinCode`, `ApplicantProfile` and `Building` — bring the
design to 3NF and BCNF. One violation, the derivable `application_id` on
`officers_deficiency`, is kept for query cost and guarded by a check constraint
instead.
